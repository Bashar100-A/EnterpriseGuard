# ADIE — Key Management

**Status:** Design proposal (not yet implemented).
**Phase:** Pre-Gate-3 gap closure (2026-10-05).
**Purpose:** Answer the auditor's first question: "who holds the private
key, and how is it managed?"
**Related:** DEC-035, DEC-044.

---

## §1 — The Gap

The project has 46 architectural decisions, but **none** addresses:

- Who holds the issuer's private key?
- How is it rotated?
- What happens if it is lost or stolen?
- How is an issuer authorized?
- How does an auditor verify a key was valid at issuance time?

An auditor will ask this in the first 5 minutes.

**This document closes that gap.**

---

## §2 — POC Level (Today)

**Current design:**

- Single RSA-2048 key pair.
- Generated by `generate_keys.py`.
- Public key distributed out-of-band.
- No rotation, no revocation, no CA.

**Adequate for Gate 3:** The POC tests verification, not key lifecycle.

**NOT adequate for production.**

### Key Lifecycle

Each key has:

| Field | Meaning |
|---|---|
| `key_id` | Unique identifier |
| `valid_from` | Start of validity |
| `valid_until` | End of validity |
| `status` | PROPOSED / ACTIVE / ROTATED / REVOKED / ARCHIVED |
| `parent_key_id` | Pointer to signing parent (null at root) |

**Rules:**

- Keys are **never deleted**. Historical verification requires them.
- Rotation is scheduled (every N months) and forced (on compromise).
- Old keys become `ARCHIVED` — usable for verification, not for issuance.

### Verification Path

An auditor:

1. Reads `signature.key_id` from certificate.
2. Looks up the operational key.
3. Verifies the key was **active at `issued_at`**.
4. Verifies the key was signed by the root.
5. Verifies the root was active at the key's issue time.
6. Traces to the Trust Anchor.

### Revocation

- Each key has a revocation status (list or transparency log).
- Auditor MUST check revocation before accepting a certificate.
- POC does NOT implement revocation.
- Production must.

### Loss / Theft

| Scenario | Action |
|---|---|
| Operational key lost | Rotate. Old certificates remain verifiable. |
| Operational key stolen | Revoke. Certificates from affected period become INVALID. |
| Root key lost | Full recovery. Existing operational keys remain valid until expiry. |
| Root key stolen | Trust Anchor must be re-established. All certificates suspect. |

## §4 — What the POC Omits

- No CA hierarchy.
- No revocation list.
- No Trust Anchor beyond a single public key.
- No key rotation.
- No key lifecycle.

**These omissions are documented, not hidden.**
