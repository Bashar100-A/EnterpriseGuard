# SIBB-Innocence Integration — Security Requirements Document (SRD)

**Project:** EnterpriseGuard ADIE  
**Component:** SIBB-Innocence Integration (`tools/sibb_innocence_integration.py`)  
**Version:** 1.1  
**Status:** Revised after security review  
**Date:** 2026-09-08  
**Methodology:** OWASP ASVS 4.0, NIST SP 800-218, STRIDE

---

## 1. Introduction

This document defines the security requirements for integrating the SIBB (Sovereign Immutable Black Box) storage layer with the Innocence Chain (`innocence_chain.py`). The integration must ensure that every innocence ring is stored immutably, replicated if distributed mode is enabled, and verified for integrity, authenticity, and chain continuity before and after storage. It must also handle encryption if configured, without weakening the existing proof chain.

This version incorporates improvements based on a deep security review, adding strict chain continuity enforcement, replay prevention, precise verification procedures, and key management guidelines.

## 2. Assets to Protect

| Asset | Description | Criticality |
|-------|-------------|-------------|
| **Innocence Rings** | Signed proof rings generated by `innocence_chain.py` | Critical |
| **Stored Ring Data** | Ring files stored in SIBB | Critical |
| **Ring Verification Keys** | Public keys used to verify signatures | High |
| **Chain State** | Current head of the innocence chain (prev_ring_hash, chain_id) | Critical |
| **SIBB Configuration** | Paths, encryption settings, node locations | Medium |
| **Audit Logs** | Records of ring storage and verification | Medium |

## 3. Threat Actors

| Actor | Description | Capabilities |
|-------|-------------|--------------|
| **Local Attacker** | Unauthorized user attempting to modify or delete stored rings | May alter files, tamper with metadata |
| **Compromised Process** | Malicious code running under same user | Forge rings or manipulate SIBB components |
| **Insider Threat** | Person with legitimate access to some nodes/shares | Tamper with replicas, attempt to rewrite history |
| **Natural Failure** | Node failure or data corruption | Loss of some replicas, integrity violations |

## 4. Security Properties (CIA + Non-Repudiation)

- **Confidentiality:** Ring data may contain sensitive information; encryption must be applied if configured.
- **Integrity:** Any modification or deletion of a stored ring must be detected and rejected.
- **Availability:** The integration must tolerate node failures and continue to serve valid rings.
- **Non-Repudiation:** Ring storage and verification events must be logged to the audit chain.

---

## 5. Functional Requirements (FR)

- **FR-1:** The integration shall provide a function `store_ring(ring_data, ring_id)` that stores a new innocence ring into SIBB storage, enforcing WORM semantics (no overwrite).
- **FR-2:** Before storing, the integration must verify the ring's signature using the trusted public key and the verification functions provided by `innocence_chain` (e.g., `verify_ring` or `verify_chain`). It must also validate the ring's `genesis_signature` and `chain_id` to prevent chain substitution.
- **FR-3:** The integration shall support both local (`sibb_storage`) and distributed (`sibb_distributed`) storage backends, selected via configuration.
- **FR-4:** If encryption is enabled in SIBB, the integration must use the configured password/key to encrypt the ring data during storage and decrypt during retrieval. Passwords must be provided via `SIBB_PASSWORD` or interactive prompt; they must not be stored in plaintext in configuration files.
- **FR-5:** The integration shall provide `retrieve_ring(ring_id)` that reads the ring from SIBB and verifies its signature and hash before returning it.
- **FR-6:** The integration shall provide `verify_stored_rings()` that checks the integrity of all stored rings and compares them against the current innocence chain state.
- **FR-7:** The integration must reject duplicate ring IDs or overwrite attempts.
- **FR-8:** The integration must validate all input paths and identifiers to prevent injection or traversal. `ring_id` must match the pattern `^[A-Za-z0-9_-]{1,64}$`.
- **FR-9:** The integration shall log all store/retrieve/verify operations via `append_activity` (excluding secret data). If `append_activity` fails, the operation must still complete but a warning must be recorded locally.
- **FR-10:** If using distributed storage, the integration must respect quorum requirements and tolerate up to `n - quorum` node failures.
- **FR-11:** **Chain Continuity Enforcement:** Before storing a new ring, the integration must verify that the `prev_ring_hash` inside the ring matches the hash of the current last stored ring (or the genesis hash if it is the first ring). If not, storage must be refused.
- **FR-12:** After successfully storing a ring, the integration must re-run `innocence_chain.verify_chain()` to ensure the whole chain remains valid. If verification fails, the integration must raise a critical error and (if possible) mark the newly stored ring as quarantined.
- **FR-13:** In distributed mode, after a successful write, the integration should attempt to synchronize any lagging nodes (if quorum is met but not all nodes received the ring). This can be done by re-writing the ring to failed nodes after a short delay.

## 6. Security Requirements (SR)

- **SR-1:** Ring data must be integrity-protected at rest by SIBB's HMAC mechanisms; any tampering must be detected on retrieval.
- **SR-2:** Signature verification must use the cryptographic verification functions from `innocence_chain` (which internally use `cryptography` library) and must be performed with the trusted public key. The public key itself must be stored outside SIBB directories (e.g., `~/.enterpriseguard/keys/public_key.pem`) and its fingerprint verified before use. Comparison of hashes (e.g., `prev_ring_hash`) must use `hmac.compare_digest`.
- **SR-3:** If encryption is enabled, ring data must be encrypted with AES-256-GCM (or equivalent) before storage; the encryption key must be derived via PBKDF2/HKDF and never stored in plaintext with the data. Key management should leverage `sibb_keys.py` or equivalent, and passwords must meet the minimum strength requirements (12+ characters).
- **SR-4:** Access to store/retrieve operations must be controlled through the same access mechanisms as SIBB (e.g., password, access key). Failure must result in generic errors and non-zero exit codes.
- **SR-5:** The integration must never silently overwrite or delete existing rings. WORM semantics must be enforced.
- **SR-6:** All file operations must be atomic and secure against TOCTOU (using O_NOFOLLOW, symlink checks).
- **SR-7:** The integration must not log sensitive information (ring contents, passwords, keys).
- **SR-8:** Temporary files, if any, must be created with 0600 permissions and deleted after use.
- **SR-9:** The integration must be resilient to metadata corruption; it should fall back to backup metadata if available and report errors.
- **SR-10:** In distributed mode, the integration must verify that a quorum of nodes agree on the stored ring's hash before considering the write successful. If `sibb_distributed` does not yet support cross-node hash comparison, this requirement is considered **not yet implemented** and must be addressed in a future update to that module.
- **SR-11:** The integration must prevent replay of old rings by verifying that the ring's `prev_ring_hash` matches the current chain head and that the `chain_id` is consistent. A ring with a different `chain_id` or mismatched `prev_ring_hash` must be rejected.
- **SR-12:** The integration must ensure that ring storage does not overwrite or conflict with other SIBB files. Rings should be stored in a dedicated subdirectory (e.g., `rings/` under SIBB base path) and their filenames must be exactly the validated `ring_id`.

## 7. Constraints and Assumptions

- **Platform:** Linux/macOS/Windows (cross-platform where possible).
- **Dependencies:** `cryptography`, `pytest`.
- **Integration:** The module will import from `tools/sibb_storage.py`, `tools/sibb_distributed.py`, `tools/sibb_keys.py` (if needed), and `tools/innocence_chain.py`. It must not modify protected directories.
- **Existing innocence_chain:** The integration should work with the current `innocence_chain.py` which already includes digital signatures and optionally TSA. The integration is an add-on storage layer, not a replacement.
- **Audit:** Must call `append_activity`; if unavailable, fallback to secure local log.
- **Key Management:** Public key for signature verification is stored in a known location (`~/.enterpriseguard/keys/public_key.pem`) or provided via configuration.
- **Encryption:** Encryption for stored rings is optional but recommended. If enabled, password/key must be provided at each operation (not cached in plaintext).

## 8. Acceptance Criteria

- All unit tests pass (to be defined in test plan).
- No High/Medium findings in Bandit.
- Rings are stored immutably; overwrite or deletion attempts are rejected.
- Signature verification occurs before storage and after retrieval.
- Chain continuity is enforced: a ring with wrong `prev_ring_hash` is rejected.
- Replay of an old ring with a different `ring_id` is rejected.
- Encryption, if enabled, works correctly and data is not stored in plaintext.
- Distributed mode respects quorum and tolerates node failure.
- Audit logging is functional for all operations.
- No secrets are exposed in logs or errors.
