```markdown
# EnterpriseGuard ADIE — Permanent Rules

This file is the authoritative, binding reference for all operational,
security, and governance rules. Every agent, tool, and human contributor
must obey these rules without exception.

**Governed by:** DC-048  
**Status:** Permanent

---

## 1. Protected Directories

The following directories are absolutely protected:

- `adie/`
- `intelligence/`
- `src/enterpriseguard/adie/`
- `src/enterpriseguard/intelligence/`

**Rules:**

- Never open, read, list, modify, or execute any file inside them.
- Use `Path.exists()` only to check existence.
- Any attempt to read or modify them is a critical violation.

---

## 2. No Automatic Activation

No component may be automatically activated without explicit owner
approval.

- Timers are installed disabled by default.
- Proposals are never self-activated.
- Any activation requires a recorded decision.

---

## 3. One Order = One Responsibility

Every execution command must contain exactly one responsibility.

- Creation, validation, documentation, and baselining are separate orders.
- Compound orders are forbidden.

---

## 4. No Trust Without Raw Evidence

No report is accepted without raw evidence.

- `stdout` and `stderr` must be shown.
- Exit codes must be captured.
- Summaries alone are rejected.

---

## 5. Sensitive Documents Are Written Manually

Sensitive foundational documents must be written and saved manually
by the owner in VSCode. They are never generated by Qwen.

Examples:

- `ARCHITECTURAL_VISION.md`
- `COMMERCIAL_ROADMAP.md`
- `PATENT_IDEAS.md`
- `TEST_RESULTS.md`
- `continuity/` files

---

## 6. Atomic Writes

All file modifications must use:

- `tempfile.mkstemp`
- `os.replace`

Direct `write_text` for critical files is forbidden.

---

## 7. No Bytecode Generation

- `PYTHONDONTWRITEBYTECODE=1` must precede every Python terminal command.
- `sys.dont_write_bytecode = True` must appear immediately after `import sys`.

---

## 8. Time Standard

All timestamps must be UTC ISO 8601 with `Z` suffix:

```
2026-09-02T08:27:41Z
```

---

## 9. Backups Before Modification

Every critical modification must be preceded by a timestamped backup:

```
<filename>.bak_<YYYYMMDDTHHMMSSZ>
```

Backups are never deleted, only archived.

Restore is performed using the most recent timestamped backup in the
same directory or in `backups/`.

---

## 10. Governance Decisions

Every significant action is recorded in:

- `tools/DECISIONS_LOG.md` with a dynamic `DC-XXX` identifier.
- `tools/activity_log.json` via `append_activity`.

Rules:

- First occurrence of an ID remains canonical.
- Duplicate IDs become `DC-XXX-SUPERSEDED-N`.
- No deletion of history.
- `DECISIONS_LOG.md` is protected by integrity monitoring and must
  never be excluded from baselines.

---

## 11. Dynamic Files Exclusion

The following files are dynamic and excluded from integrity monitoring:

- `tools/activity_log.json`
- `tools/errors.log`
- `tests/TEST_RESULTS.md`
- `continuity/CURRENT_STATE.md`

`tools/DECISIONS_LOG.md` is NOT excluded. It is a protected governance
record and remains under integrity monitoring.

---

## 12. Audit Chain

`activity_log.json` is protected by a hash chain.

- Writes go only through `append_activity`.
- Direct writes are forbidden.
- Periodic verification is performed by `audit_chain.verify_chain()`
  during `checklist.py` or `integrity_monitor.py` checks.

---

## 13. Test Result Logging

Every unit test run must be recorded in:

```
tests/TEST_RESULTS.md
```

The latest result per component is authoritative. Old rows are never
deleted.

---

## 14. Stop Condition

Any critical error stops execution immediately.

- No further steps.
- Report to owner.
- Restore from the most recent timestamped backup in the same directory
  or in `backups/`.

---

## 15. Owner Authority

The owner is the final authority.

- The owner can override any technical recommendation.
- No irreversible action is taken without owner approval.

---

## 16. Critical Files Are Never Deleted

Critical files must never be deleted. They may only be archived or
superseded.

Critical files include:

- `tools/TRUSTED_BASELINE.json`
- `TRUSTED_BASELINE_SENTINEL.json`
- `tools/integrity_baseline.json`
- `integrity_baseline_sentinel.json`
- `tools/genesis_baseline.json`
- `tools/hardware_identity.json`

Deletion of any critical file is a governance violation.

---

## 17. Digital Signatures for Release Files

Critical release files must be GPG-signed and verified before final
acceptance.

Signed files include:

- `VERSION`
- `CHANGELOG.md`
- `tools/TRUSTED_BASELINE.json`
- `TRUSTED_BASELINE_SENTINEL.json`
- `tools/integrity_baseline.json`
- `integrity_baseline_sentinel.json`

Verification is performed using `tools/sign_release.py --verify`.

---

## 18. No Secrets in Repository

No private keys, passphrases, or secrets shall ever be stored in the
repository.

- GPG keys reside outside the project directory.
- Hardware identity keys are the only allowed identity artifacts, and
  they are permission-locked to `0600` or `0400`.

---
## 19. Digital Signatures for Innocence Chain
- Every innocence ring must be signed with the project's RSA-2048 private key.
- The private key must be stored outside the repository (e.g., `~/.enterpriseguard/keys/private_key.pem`) with permissions `0600`.
- The public key must be available for verification (`~/.enterpriseguard/keys/public_key.pem`).
- Rings without valid signatures are rejected by default; use `--allow-unsigned` only for legacy chain inspection.
**End of Permanent Rules.**
```
